# Contributing to tsops

Thank you for improving tsops. The project values small, testable changes that strengthen one typed application graph from local development to Kubernetes.

Read [`ROADMAP.md`](ROADMAP.md) and [`ARCHITECTURE.md`](ARCHITECTURE.md) before adding a new product surface. Features outside the documented boundary should start as a focused issue rather than a large implementation pull request.

## Set up the repository

Requirements:

- Node.js 24 or newer
- Corepack
- Docker and `kubectl` only for integration work that uses them

```bash
git clone https://github.com/Pom4H/tsops.git
cd tsops
corepack enable
pnpm install --frozen-lockfile
```

## Required checks

Run these before opening or updating a pull request:

```bash
pnpm lint
pnpm typecheck
pnpm test
pnpm docs:build
```

- **Biome** owns repository linting and formatting.
- **TypeScript project references** compile and type-check the packages.
- **Vitest** covers domain and adapter behavior.
- **VitePress** must build with valid internal links.

Apply safe formatting and lint fixes with:

```bash
pnpm format
pnpm lint:fix
```

Do not disable a rule or documentation check merely to make a pull request green.

## Development workflow

1. Create a branch from `main`.
2. Add or update tests before changing public behavior.
3. Keep external effects behind the ports in `@tsops/core` and implementations in `@tsops/node`.
4. Update one maintained example or guide for a public workflow.
5. Add a Changeset when a published package changes.
6. Run the required checks.
7. Open a pull request with the motivation, behavior, tradeoffs, and explicit non-goals.

## Changesets

Use Changesets for user-visible package behavior:

```bash
pnpm changeset
```

Choose the smallest correct SemVer bump and explain the change in user language. Documentation-only repository changes do not need a Changeset unless they accompany unpublished package behavior.

Package versions and changelogs are generated by the release workflow. Do not manually create release tags or edit versions as a substitute for a Changeset.

## Design checklist

### Product boundary

- Does the change remove duplicated application topology?
- Does it improve continuity between local, preview, and Kubernetes runtimes?
- Is it application delivery rather than cluster or cloud provisioning?
- Can an existing focused tool be composed instead?

### Type safety

- Preserve literal application, namespace, Secret, and ConfigMap keys.
- Prefer inference and explicit domain types over overloads that weaken IntelliSense.
- Avoid new `any` and unsafe casts in public or core code.
- Add compile-time valid and invalid cases when public types change.

### Determinism

- Names, manifests, endpoint resolution, image keys, and structured output must be stable for the same inputs.
- Process globals and current time enter through explicit providers where they affect domain behavior.
- Dry-run behavior must not perform hidden external mutations.

### Errors

- Fail before side effects when input is invalid.
- Include the application, namespace, resource, or command context needed to act.
- Never print Secret values or credentials.
- Keep domain diagnostics structured until the CLI presentation layer.

### CLI

- Use predictable option names across commands.
- Preserve stable exit semantics.
- Add `--dry-run` or an equivalent plan boundary to mutating workflows.
- Do not make automation parse emoji-formatted human output when a structured result can be exposed.

### Documentation

- Update the closest guide and source example.
- Link to maintained files instead of copying a large config into several pages.
- Use Node.js 24 in current CI and setup snippets.
- Avoid invented testimonials, unsupported claims, and placeholder repository links.

## Useful example checks

```bash
pnpm tsops plan --config examples/fullstack/tsops.config.ts --dry-run
pnpm tsops build --config examples/monorepo/tsops.config.ts --dry-run
pnpm tsops up preview \
  --config examples/preview-namespaces/tsops.config.ts \
  --var pr=42 \
  --include worken-front \
  --dry-run
```

Use fake adapters for deterministic tests. Real cluster access should be necessary only for dedicated integration validation.

## Pull request scope

Prefer one coherent change over a bundle of unrelated cleanup. Remove obsolete code and documentation made redundant by the change. Do not leave parallel APIs “for later” unless backward compatibility requires them and the deprecation path is documented.

Large provider abstractions, hosted services, or agent-specific packages need demonstrated demand and an architectural discussion first.

## Conduct

Be direct, respectful, and specific. Review the code and the decision, not the person.
